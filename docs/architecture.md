# Architecture — مواصلاتي مصر

## Overview

```
                 ┌────────────────────────────┐
   Browser ─────▶│  Next.js web  (:3000)      │── /api/* rewrite ──┐
                 └────────────────────────────┘                    │
                 ┌────────────────────────────┐                    ▼
   Browser ─────▶│  Next.js admin (:3002)     │── /api/* rewrite ──▶ Express API (:3001)
                 └────────────────────────────┘                    │
                                                                    ▼
                                              Database interface (src/db/types.ts)
                                              ┌──────────────┬──────────────────┐
                                              │ MemoryDatabase│  PrismaDatabase  │
                                              │ (seeded demo) │  (PostgreSQL)    │
                                              └──────────────┴──────────────────┘
```

Both frontends call **relative** `/api/*` paths; Next.js rewrites proxy them to the backend.
This keeps browser code origin-agnostic (reverse-proxy friendly) and avoids CORS entirely for
same-origin deployments.

## Backend layers

```
src/
├── index.ts / app.ts        # bootstrap + Express wiring (helmet, cors, rate-limit, pino)
├── middleware/              # error handler (ApiError + Zod), JWT auth/roles
├── routes/                  # HTTP handlers: routes, stops, cities, modes, search,
│                            # trips, reports, health, auth, admin
├── services/
│   ├── routing-engine.ts    # ★ multimodal Dijkstra planner (pure functions)
│   ├── trip-planner.ts      # orchestration: geocode → graph → plan → record history
│   └── geocoder.ts          # local gazetteer (Arabic-normalized) + Nominatim fallback
├── db/
│   ├── types.ts             # Database interface (repository contracts)
│   ├── memory-db.ts         # zero-config seeded implementation
│   ├── prisma-db.ts         # PostgreSQL implementation (lazy-loaded)
│   └── index.ts             # driver factory (DB_DRIVER / DATABASE_URL)
├── database/
│   ├── seed-data.ts         # ★ single source of truth for demo data (framework-agnostic)
│   └── seed.ts              # Prisma seeder mapping seed-data → PostgreSQL
└── utils/                   # env, logger
```

### Key decisions

1. **Driver-agnostic data layer.** Every handler depends on the `Database` interface, never on
   Prisma directly. Result: the entire API (and its 54 tests) runs with zero external
   infrastructure, while production uses PostgreSQL via Prisma without touching handler code.
2. **One seed dataset.** `seed-data.ts` feeds *both* the in-memory DB and the Prisma seeder, so
   dev, CI, and production share identical demo data.
3. **Pure routing engine.** `routing-engine.ts` has no I/O — it consumes plain arrays and
   returns plain objects, making it trivially unit-testable.
4. **Security baseline.** Helmet, CORS allowlist, rate limiting, JWT with role checks
   (`USER`/`DATA_ADMIN`/`MODERATOR`/`SUPER_ADMIN`), audit log for every admin mutation.

## Routing engine

Graph model:

- **Nodes** are `(stop, currentRoute|onFoot)` states.
- **Ride edges** run along each route in both directions; continuing on the same vehicle costs
  travel time only, while boarding adds wait time (5 min), a transfer penalty (2 min) and the
  route fare.
- **Walk edges** connect stops ≤ 700 m apart and link origin/destination to stops within 1.5 km.
  Total walking per trip is capped (1.6 km) so walk-only chains can't dominate results.

Mode-aware Dijkstra minimizes a **lexicographic cost tuple**:

| Mode | Tuple order |
| --- | --- |
| `FASTEST` | time → transfers → fare → walking |
| `CHEAPEST` | fare → time → transfers → walking |
| `FEWEST_TRANSFERS` | boardings → time → fare → walking |
| `LEAST_WALKING` | walking → time → fare → boardings |

Alternatives are generated by re-running the search with the previous solution's dominant route
banned (up to 3 distinct trips). Short origin→destination pairs (≤ 1.2 km) also get a
direct-walk suggestion.

Fares: `FIXED/STAGE/ZONE` use the recorded fare (default 5 EGP if missing); `DISTANCE_BASED`
charges `max(baseFare, 0.5 EGP/km)`.

## Data quality model

- Every route carries `confidenceLevel` (`HIGH/MEDIUM/LOW/UNVERIFIED`), `dataSource`, and
  `lastVerifiedAt`; the UI surfaces these as trust badges.
- Admin mutations (fare/hours/status edits) append to the `DataUpdate` changelog automatically.
- Community reports flow `PENDING → REVIEWING → APPROVED/REJECTED → RESOLVED` and every
  moderation action lands in the audit log.

## Arabic text handling

Search and geocoding normalize Arabic (strip diacritics/tatweel, unify أإآ→ا, ى→ي, ة→ه) so
"الاسماعيلية" matches "الإسماعيلية". The local gazetteer (cities + areas + stops) resolves
queries offline; OpenStreetMap Nominatim is an optional fallback (`GEOCODING_ENABLED=false`
disables it fully for offline operation).
